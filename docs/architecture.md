# Architecture

ForgeMQ v1 is one process. `New` keeps one log per topic in memory. `Open` stores that log under a directory: `data/<topic>/000000.log` and the following segments, plus `metadata/groups.log` for committed group offsets. A published message is appended and given the next offset, starting at 0. The record keeps an id, the topic, an optional key, headers, the payload, and the time it was accepted. On disk each record also has a length and a CRC-32. `Publish` returns after that record is synced. `PublishBatch` assigns the next offsets, writes every record that fits in the active segment, and syncs that segment once. A batch larger than the segment rolls and syncs again. A single `Publish` is the same path with one record. A segment rolls after it passes the configured size, which defaults to 1 MiB. The guarantee is at-least-once. A batch that fails after a segment has synced can leave that prefix on disk.

A subscription group is a name plus the next offset that group has not finished. Creating the group starts at the earliest offset still in the log, including when messages were published first. Each group therefore receives every retained message. `Receive` waits when the group has caught up, or when it already holds its prefetch count of unacknowledged deliveries. The default prefetch is one. Two consumers in the same group share that in-flight set, so one message is handed to one of them.

`Ack` finishes a delivery. The group's offset moves forward only through a contiguous run of finished offsets, so an earlier delivery can be acknowledged after a later one when prefetch is greater than one. `Nack(true)` puts the same log offset at the front of the group's queue and counts another attempt. `Nack(false)` appends the record to `<topic>.dlq` immediately. The attempt that reaches the limit is appended there instead of being queued again. A timer does the same as `Nack(true)` when the delivery is still outstanding. The dead-letter record keeps the key, payload, and headers, and adds `forgemq-original-topic`, `forgemq-original-offset`, `forgemq-attempts`, and `forgemq-reason`. A second `Ack` or `Nack` returns `ErrSettled`.

Opening a directory reads every topic segment, checks each record, and drops a torn tail. A bad checksum with more bytes after it stops recovery. Group offsets are restored from the highest committed value, so a message that was delivered but not acknowledged is delivered again. A segment file is deleted only when every current group has committed past its last offset. `Close` makes a waiting `Receive` return. Publishing to a missing topic fails. Creating a topic twice fails.

`Listen` accepts TCP connections. `ListenTLS` wraps those connections. Each request is one frame: a length, a CRC-32, and a body that names the command. A client can create a topic, publish, subscribe, receive, acknowledge, and poison a delivery. The server hands a message to a connection only when that connection asks for one. `Publish` still returns only after the broker has accepted the record. If the connection drops, the server puts every unacknowledged delivery back on the group's queue, and the client's next `Receive` dials again and continues from the stored offset.

When principals are configured, the first command is an authentication frame. A token allows publish, consume, or both, and a command outside that right is refused. A connection past the connection limit is closed. A subscription past the per-connection limit, and a topic past the topic limit, are refused. `Poison` dead-letters that delivery at once with reason `poison`; another group still reads its own copy. Counters since open are available from `Stats`. A configured logger records dead letters, refused commands, and limit breaches as structured lines, without the payload or the token. `InjectPublishFaults` fails a publish before the record is appended.

`ReceiveN` waits until one delivery is available, then returns further records already in the log without passing the group's prefetch. The benchmarks in the package measure one publish, a synced publish, a synced batch, concurrent publishers, and a consumer draining the log. `-benchmem` reports allocations. A memory profile is an output of the benchmark command, not a file the broker keeps.

One process owns the log. v1 does not run as a cluster.
